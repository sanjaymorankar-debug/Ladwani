**CONFLICT** means the rebuild does something you decided against. Examples:
- a rejection without a reason;
- any member can see any family's member list and tree;
- anyone can list in the marriage bureau, including under-age and married members;

**What this means.** The rebuild is a broad app: bookings, payments, fees, a social feed and a bureau. But it was built without the workbook. Most of the workbook's governance is absent:
- dual blind approval;
- district-scoped Operators;
- Karta rules;
- the tree builder;
- organisations and bodies;
- data rights.

PR #10's logic ports mostly one to one, roughly 3,000 lines of rules. It has to be rewritten as Nest services on the rebuild's snake_case schema, and the tests rewritten as Jest integration specs. **Rough size:** a port of the same order as PR #10 itself, in seven phases.

## 2. Facts about the rebuild that shape everything

1. **Sign-in and roles come from the hub.** A hub sign-in grants MEMBER, KARTA, OPERATOR or ADMIN and **never removes them** (`apps/api/src/auth/auth.service.ts:95-100`, checked). The resulting roles have no scope: a Karta is tied to no family and an Operator to no district. A first hub sign-in creates an ACTIVE account with no mobile and a placeholder name, so it skips registration and approval.
2. **A user's status is never re-checked after sign-in.** `refresh()` keeps issuing tokens to suspended or deleted users (`auth.service.ts:225-249`, checked).
3. **The approval queue has one reviewer, with no scope.**
   - Every Operator sees every request's raw data.
   - A reviewer can decide their own submission (`common/approvals/approvals.service.ts:56-65`, checked).
   - A rejection needs no reason (`approval-queue/dto/decide-approval.dto.ts`, checked).
   - The per-action approver role is seeded but never enforced.
4. **Areas and links are missing.** There is no TALUKA or VILLAGE in the location master, and members and families are never linked to an area. So nothing can be routed to "the Operators of the district" yet.
5. **The building blocks are absent:** no settings table, no scheduler, no email or SMS delivery. Uploads are stored unencrypted on the hub's local disk, with a default signing secret, and are not covered by any backup.
6. **No full Aadhaar or ID number is stored anywhere.** The rebuild has no ID-proof model, so OP-01 is built in from the start.
7. **LadWani production is not deployed yet** (hub `DEPLOY.md`). Every finding above affects the test tier only.

### 0. Facts about the rebuild that shape every row

1. **Sign-in is the hub, and roles come from the hub.**
   - `POST /auth/hub` (`apps/api/src/auth/auth.controller.ts:46-54`) → `AuthService.hubLogin` (`apps/api/src/auth/auth.service.ts:59-115`).
   - It maps the hub role `member|karta|operator|admin` to `MEMBER|KARTA|OPERATOR|ADMIN` (`auth.service.ts:26-31`).
   - It grants that role at every sign-in and **never removes it** (`auth.service.ts:95-100`).
   - The hub's role list for LadWani is `member,karta,operator,admin` (`bkesari-platform/portal/sql/hub_schema.sql:19`). The hub's access admin grants and revokes them (`portal/hub.js:263-310`).
   - LadWani itself has **no role-management API or page**. The only `userRole.create` calls are in hub login, register and family-create approval (`apps/api/src/family/family.service.ts:312`).
   - The first Admin is made by SQL (`bkesari-platform/database/ladwani/03_ladwani_first_admin.sql`).
2. **Hub-made accounts skip registration.**
   - A first hub sign-in creates `users.status='ACTIVE'`, with no mobile and `members.first_name = <email local part>` (`auth.service.ts:85-91`).
   - No gender, DOB, Mul Gaon, consent or approval is involved.
3. **The access token is a 15-minute HS256 JWT** carrying `{sub, roles, memberId}` (`auth.service.ts:112, 219`).
   - `JwtStrategy.validate` returns the payload as is (`apps/api/src/auth/strategies/jwt.strategy.ts:23-25`).
   - `PermissionsGuard` re-reads permissions from the DB on every request (`apps/api/src/common/guards/permissions.guard.ts:23-55`).
   - **`users.status` is never checked after login.** The only reads are in `login` and `hubLogin`. `refresh` (`auth.service.ts:225-249`) checks neither `status` nor `deletedAt`.
4. **The location data is there but unused.**
   - `areas` has types `COUNTRY|STATE|DISTRICT|CITY|AREA|GROUP` (`packages/shared-types/src/enums.ts:96-97`; `apps/api/prisma/schema.prisma:448-467`).
   - `member_areas` and `family_areas` are **never written** by any API code. Only `viewer-context.service.ts:15-23` and `reports.service.ts:28` read them.
   - So `SAME_AREA` and the Operator's `ADMIN_OPERATOR` area scope (`apps/api/src/common/privacy/visibility.ts:32-52`) never match anyone.
5. **Approvals use one engine with a single reviewer** (`apps/api/src/common/approvals/approvals.service.ts`, `apps/api/src/approval-queue/*`).
   - `approval_rules.approver_role` is seeded (`apps/api/prisma/seed.ts:35-45`) but **never enforced**: a grep for `approverRole` in `src` finds only the schema.
6. **There is no scheduler.** In the hub, every `/ladwani/...` request, API included, passes the hub's sign-in gate (`portal/ladwani.js:150-161`). A Hostinger cron `curl` to an API endpoint, as PR #10 did for `/api/cron/approval-sla`, **cannot reach LadWani** without a hub change.
7. **There is no email or SMS delivery.** `NotificationsService` is in-app only (`apps/api/src/notifications/notifications.service.ts:16-36`), and the sign-up OTP is returned in the response outside production (`auth.controller.ts:20-26`). Every "send by email/SMS" requirement, including Admin 2FA, needs a delivery channel the rebuild does not have.
8. **Migrations.**
   - The rebuild has only `20261024000000_postgres_baseline` and `20261025000000_hub_user_id` (`apps/api/prisma/migrations/`).
   - Production `bk_ladwani` was loaded from raw SQL (`bkesari-platform/database/ladwani/postgres/README.md`), so `_prisma_migrations` on each Neon branch must be checked and resolved before any `prisma migrate deploy`. I did not query it; this needs checking.
   - All column names are snake_case with `@map`. New PR #10 columns must be renamed: `"fromMemberId"` style becomes `from_member_id`.
9. **Web pages run only in the browser.** Pages are client components. `[param]` routes use `page.tsx` + `generateStaticParams() → [{id: PLACEHOLDER}]` + `view.tsx` under `ClientOnly` (`apps/web/src/app/members/[id]/page.tsx`; `apps/web/src/lib/route-params.ts`). All new logic goes in Nest.

### 2. Stop-and-ask items (owner approval needed before porting)

1. **Login: where Admin 2FA lives (decision 1).** The owner approved "Admin 2FA", but the live login is now the bkesari hub (Neon Auth). Either the hub enforces a second factor for LadWani admins, which changes the hub's login for every project, or LadWani adds a step-up after hub sign-in. Both change how login works. Both also need an email/SMS provider the rebuild does not have (§0.7).
2. **Which system owns roles (CONFLICT, F32).**
   - Today the hub grants ADMIN/OPERATOR/KARTA into LadWani on every sign-in and never removes them (`auth.service.ts:95-100`).
   - The workbook and PR #10 have the LadWani Admin assign roles, including district/state-scoped ones, with a 2-Admin floor.
   - Proposal: make LadWani `user_roles` authoritative, stop `hubLogin` granting ADMIN/OPERATOR/KARTA, and use the hub role only to let a person in. This changes login and removes the hub grant feature.
   - It also raises a data question: should hub-granted ADMIN/OPERATOR/KARTA rows already in production be kept or revoked? A hub "karta" grant creates an unscoped KARTA row with `family_id NULL`.
3. **Hub sign-ups and F01 (CONFLICT).** First hub sign-in creates an ACTIVE account with no mobile and a placeholder name (`auth.service.ts:85-91`). Two questions:
   - Should new hub users start as DRAFT and complete registration (mobile + OTP, gender, DOB, Mul Gaon, ID proof, dual approval)?
   - Do accounts already created through the hub count as "pre-P1, stay ACTIVE" (P1 §11)?
4. **Status gating on existing routes.** Adding the DRAFT gate to ~11 routes, and checking status in `JwtStrategy`/`refresh`, changes what today's PENDING users can do: currently they can log in and use everything.
5. **Operator narrowing (decision 3, CONFLICT).** This removes `audit:view` and `report:view` from OPERATOR, removes `audit:view` from ASSET_OWNER, and scopes `/approvals` to mapped districts. It takes away existing capability. `seed.ts:133-135` will delete the grants on the next seed.
6. **Data export (F33, CONFLICT).** Moving the four report CSV exports from `report:view` to ADMIN/`DATA_EXPORT` removes them from Operators.
7. **Removing direct Mul Gaon editing (F08).** For ACTIVE users, `native_village/district/state` would no longer save from `PATCH /members/me`.
8. **Generic approval queue.** Three changes to existing behaviour:
   - make the note mandatory for reject/return (the owner already decided "every rejection gives a reason"; confirm it applies to the rebuild's queue);
   - block deciding one's own submission;
   - enforce `approval_rules.approver_role`, so ADMIN-only actions such as `family.karta.transfer` and `asset.suspend` could no longer be decided by an Operator.
9. **Location data.** Re-typing existing CITY/AREA/GROUP rows as DISTRICT/VILLAGE, or backfilling `members.native_area_id`/`member_areas` from free-text `native_*` columns, rewrites data (and would guess names). Proposal: no backfill.
10. **Education and occupation model.** Keep `members.education_level_id`/`occupation_id` and add `education_records` beside them (no drop or rename). Ask if a merge is wanted later.
11. **SLA escalation trigger (F06).** Every `/ladwani/api` request passes the hub gate, so a cron URL needs either a hub change (an exempt, secret-checked path) or an in-process timer. A hub change is outside LadWani.
12. **Where encrypted ID proofs are stored (F03).** The rebuild only has dev local-disk storage at `process.cwd()/uploads-dev` (hub root on Hostinger). Proofs need persistent, backed-up storage (R2, or a fixed path outside the deploy) and an `ID_PROOF_KEY`.
13. **Password login and register routes behind the hub.** `/auth/login`, `/auth/register` and `/auth/verify-otp` stay reachable under `/ladwani/api/v1/` for signed-in hub users, so one person can hold a second password account. Keep or remove them? Removing a route needs approval.

### Things that affect every flow

1. **Three sources for the Karta, nothing keeps them in step, and the database guards none of them:**
   - `families.karta_member_id` (`schema.prisma:174`);
   - `family_members.is_karta` (`schema.prisma:327`);
   - a `user_roles` row with role KARTA and `family_id` (`schema.prisma:104-119`).

   Authorisation uses only the third one: `FamilyAuthorizationService.isKartaOf` (`common/family-authorization/family-authorization.service.ts:13-16`). That role is granted only when the `family.create` approval is approved (`family/family.service.ts:301-318`). Every Karta-change flow (F12, F16, F17, F22) must update all three in one transaction.
2. **Permissions are global, not tied to a family or district.**
   - `PermissionsGuard` (`common/guards/permissions.guard.ts:37-49`) only asks "does any role give X".
   - The hub login grants the hub's role without any scope (`auth/auth.service.ts:26-31`, `:95-99`). A hub "karta" becomes a KARTA with no family; a hub "operator" becomes an OPERATOR with no district.
   - Per-record checks exist only for the Karta. There are no Operator-of-district checks anywhere: `user_roles.area_id` exists but is never read outside the privacy helper.
   - Yet F16 (vacancy), F18, F22 and the review queue all need "an Operator of the family's district".
3. **A family has no district.** `family_areas` exists (`schema.prisma:481-496`), but `createFamily` never fills it. `native_district` is free text (`family.service.ts:57-58`). Without a district, nothing can be routed to the right Operator.
4. **There is no `settings` store.** The port needs these PR #10 settings:
   - `family.join_request_expiry_days` (30);
   - `tree.ancestor_levels` (3, OP-02);
   - `deceased.certificate_required` (off until go-live);
   - `approval.sla_days` (7).

   The P1 port probably needs the same table. **Create it once and coordinate with the P1 agent.**
5. **There are no scheduled jobs.** Join-request expiry (F15) and the vacancy SLA alert (F16) need a daily run. The hub already uses `crontab` (`bkesari-platform/DEPLOY.md:188`). Port PR #10's `/api/cron/daily` as a Nest controller that checks an `x-cron-secret` header, and also check expiry when the data is read.
6. **The review queue** (`approval-queue/*`, `common/approvals/approvals.service.ts`) is shared by F10, F12, F16 and F23. Three things are missing:
   - it never applies `approval_rules.approver_role`;
   - it has no district scoping;
   - it lets a reviewer decide without a note.

   See §3 (S4, S5). The owner's decisions "Admin review of a Karta hand-over" (P2 §9) and "every rejection gives a reason" (P2 §11) depend on fixing it.
7. **The relationship master is short and its inverses are wrong for women.**
   - `seed.ts:14-31` has 16 types; the workbook's Relationships sheet in PR #10 has 44 (`prisma/migrations/20261025100000_workbook_phases/migration.sql:465+`).
   - There are no maternal grandparents, great-grandparents, uncles, aunts, nephews, nieces or in-law siblings.
   - There are no `local_name`, `generation`, `side` or `link_type` columns.
   - Each type has a single inverse, and for women it is the male one: `mother→son`, `daughter→father`, `sister→brother`, `grandmother_p→grandson`, `granddaughter→grandfather_p`, `daughter_in_law→father_in_law`, `mother_in_law→son_in_law`. The same defect as PR #10 P3 §1e-2.
   - `RelationshipsService.linkMembers` (`common/relationships/relationships.service.ts:28-33`) writes that inverse as it is.
   - The codes differ from PR #10: the rebuild has `grandson`/`granddaughter`, PR #10 has `grandson_sons_son` and so on. **Keep the rebuild's codes** and add the missing rows. Do not rename.

### 5. Pre-check SQL for the rebuild database (read-only, snake_case)

```sql
-- Q1 families with more than one active Karta (blocks A2)
SELECT family_id, count(*) FROM family_members WHERE is_karta AND left_at IS NULL GROUP BY family_id HAVING count(*) > 1;
-- Q2 people who are active Karta of more than one family
SELECT member_id, count(*) FROM family_members WHERE is_karta AND left_at IS NULL GROUP BY member_id HAVING count(*) > 1;
-- Q3 the three Karta sources out of step
SELECT f.id, f.karta_member_id, fm.member_id AS is_karta_member, m.user_id,
       EXISTS (SELECT 1 FROM user_roles ur JOIN roles r ON r.id = ur.role_id
               WHERE r.code = 'KARTA' AND ur.family_id = f.id AND ur.user_id = m.user_id) AS has_role
  FROM families f
  LEFT JOIN family_members fm ON fm.family_id = f.id AND fm.is_karta AND fm.left_at IS NULL
  LEFT JOIN members m ON m.id = fm.member_id
 WHERE f.deleted_at IS NULL AND (f.karta_member_id IS DISTINCT FROM fm.member_id);
-- Q4 wrong-gender relationship rows (A3)
SELECT mr.id, rt.code, m.gender FROM member_relationships mr
  JOIN relationship_types rt ON rt.id = mr.relationship_type_id
  JOIN members m ON m.id = mr.from_member_id
 WHERE (rt.gender_applicable = 'MALE' AND m.gender = 'FEMALE') OR (rt.gender_applicable = 'FEMALE' AND m.gender = 'MALE');
-- Q5 married spouses still recorded as unmarried (A11)
SELECT mr.id, m2.id, m2.marital_status FROM marriage_records mr JOIN members m2 ON m2.id = mr.member_id_2
 WHERE mr.status = 'MARRIED' AND m2.marital_status <> 'MARRIED';
```

### 2. Stop-and-ask items (owner approval needed before the port)

1. **Groups → organisations (F26b).** The rebuild has no groups, and its cutover is a clean start (`docs/23-production-cutover-plan.md:14`). Choose one:
   - **(a)** drop the conversion;
   - **(b)** import groups and rosters from the old database export, matching people to hub accounts by email or mobile.

   (b) means importing old personal data into the new database, which the rebuild's plan rejected.
2. **The `GROUP` area type** ("Local Group", unused): keep it, retire it, or treat it as the source of organisations? Retiring it means removing an enum value from `AREA_TYPES` and the admin config UI. That removes a feature, even an unused one.
3. **Operators become district-scoped.** F26 (Operators of the district), F29 (Operator of the district or state appoints body office bearers) and the P0/P1 decisions need `user_roles.area_id` written for Operators. Today OPERATOR is global and comes from the hub token (`auth.service.ts:95-100`). Who maps Operators to districts: the LadWani Admin in the app, or the hub? Narrowing Operators removes existing capability (every Operator can review every approval today, `approval-queue.service.ts:30-35`).
4. **Hub role sync is add-only.** A seat-derived role must be revoked inside LadWani, while hub roles are never revoked (`auth.service.ts:95-100`). Changing this sync changes how login assigns roles, so it is a login change.
5. **Replacing the single-reviewer approval for organisations** with the two-Operator blind round. This is the same decision as P1: the generic `approvals` engine stays for the other actions, or is replaced. The workflow doc (`docs/12-approval-workflow.md`) describes one reviewer.
6. **Adding TALUKA** (and possibly VILLAGE) to the area hierarchy. The rebuild documents Country → State → District → City → Area → Local Group (`docs/02-feature-map.md:44`). The owner's chain is State › District › Taluka. The change is additive, but it changes the documented location model, and existing City/Area rows would need re-parenting under talukas. That is a data rewrite if any exist on dev/test.
7. **Uploads encrypted at rest** for organisation certificates (P4 §e). The rebuild stores every file in plain form on local disk (`uploads/dev-file-storage.service.ts:8`, `uploads.service.ts:77`). Pick a key-management approach: an ID_PROOF_KEY-style env key on the hub, or R2 server-side encryption.
8. **A scheduler for the F31 term-end job:** an in-process scheduler inside the hub process, or crontab calling a secret-protected endpoint. This adds a new runtime component and environment key.

### 2. Stop-and-ask items (owner approval needed before the port)

1. **Community-wide posts must wait for approval (D-P5-4 vs the rebuild).** Applying the decision means changing the seeded `post_types.requires_approval` rows (GENERAL, EVENT, HELP_REQUEST, CONDOLENCE are false today), or ignoring that flag for COMMUNITY audience. That is a data change and a visible behaviour change on the live rebuild. Confirm that the PR #10 decision applies to the rebuild.
2. **Existing area-targeted posts** (`posts.target_area_id`): should they be backfilled to the DISTRICT / STATE audience (data rewrite), or kept as a legacy "area" audience? And should the column stay?
3. **Bureau eligibility on existing listings:** profiles now visible that fail legal age, OP-08 status or earning. Hide them in search only (PR #10's choice; no row change), or set `is_visible = false` (data rewrite)?
4. **What "earning" means in the rebuild.** The rebuild has no social or employment status. It has `occupation_id` (STUDENT, HOMEMAKER, RETIRED, NOT_WORKING …) and `income_range` with bands that differ from PR #10. Options:
   - derive earning from occupation + income band;
   - add a new `members.is_earning` or social-status column.
5. **Restricting browsing to listed members and their Karta (D-P5-2).** This removes bureau access that every member has today, and changes the directory's `matrimonyAvailable` filter (remove it, or restrict it to the same audience).
6. **The CONTACT_REQUEST flow and `allowContactRequests`** (a rebuild-only feature). The workbook shares contact on an accepted interest, following the contact preference. Keep both, merge them, or remove CONTACT_REQUEST? Removing it is removing a feature.
7. **`report:view` for Operators.** Making the global reports (including financial) Admin-only per D-P6-1 removes an existing route for Operators.
8. **`audit:view` for OPERATOR and ASSET_OWNER** (unscoped, includes raw request bodies). Remove it or scope it? Either way this removes access.
9. **F40 deletion with hub sign-in (changes how login works).** After anonymisation, the person's bkesari ID still exists, and `hubLogin` will create a new ACTIVE LadWani account and re-grant the hub role. Pick one:
   - (a) tombstone `hub_user_id` and refuse re-entry;
   - (b) also delete or disable the bkesari ID in the hub (another project);
   - (c) allow a fresh start.
10. **Erasing PII from `audit_logs.new_value`.** The interceptor stores raw request bodies. D-P6-3 keeps the audit log; does keeping it override erasure of the person's data inside it? This decides whether the anonymiser may rewrite audit rows. Separately, it decides whether the interceptor should stop storing raw bodies from now on.
11. **District / State / National teams and body officers do not exist in the rebuild.** There are no organisations (P4) and no STATE_TEAM / DISTRICT_TEAM roles; the hub maps only member, karta, operator and admin (`auth.service.ts:26-31`). F36 body moderation and F39 scoping need those roles. That means new hub roles, or roles managed in LadWani. This touches login and role mapping.
12. **File storage for photos and the backup.** Uploads go to the hub's local disk today. Moving to the hub's S3 bucket, or another provider, is an infrastructure decision (and outside this repo).
13. **The CSP lives in the hub repo (`portal/ladwani.js`).** Confirm the hub owner accepts a LadWani-specific header block. Confirm also whether the local password routes `/auth/register`, `/auth/verify-otp` and `/auth/login` should stay mounted inside the hub (removing them is a login change).
